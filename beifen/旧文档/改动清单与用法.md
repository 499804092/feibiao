# feibiao —— 飞镖视觉→飞控板 改造包（含识别逻辑审查与修复）

## 这个文件夹是什么

按需求改造后的代码副本。**原始工程 `2024_Dart_Algorithm/` 没有改动**，本文件夹是独立的一份。

两件事：
1. **数据结构改造**：视觉端下发给飞控板的数据结构体，包含 `pitch`、`yaw`、`roll` 和到目标的直线距离 `distance`。
2. **识别逻辑审查与修复**：查出并修掉了识别链路里的致命 BUG（详见下面）。

### 📌 三份文档，按这个顺序看

| 文档 | 内容 |
|---|---|
| **`识别逻辑逐行讲解.md`** | ← **先看这个**。识别链路完整代码 + 逐行中文讲解 + 8 个问题（含 1 个致命 BUG）的审查结论与实测数据 |
| `飞镖视觉解算全流程逻辑总结.md` | 整条数据链路（取图→检测→跟踪→解算→串口→飞控→电机）+ 下发 22 字节帧的完整说明 |
| `改动清单与用法.md` | 本文件：目录结构、编译步骤、上车检查清单、常见问题 |

### ⚠️ 审查结论（实测，不是推演）

**识别逻辑确实有致命问题**：负责把网络输出坐标换算回原图坐标的 `fitRec()`，**写了却从来没有被调用**。

| 项目 | 数值 |
|---|---|
| 不调用 `fitRec` 时的目标位置最大误差 | **240.6 像素**（x 方向最大 197 px = 原图宽度的 **51%**） |
| 对单目测距的影响 | **偏大 1.667 倍**（2.13 m 的靶报成 3.56 m） |
| 修复后（调用 `fitRec`）的还原误差 | **1.042 像素** |

另外还有：框不裁剪、类别号是魔法数字、浮点转 int 的未定义行为、`fitRec` 缺除零保护
（以上 5 个已在 `feibiao/` 里修好），以及**无锁栈 ABA 隐患**（未修，需你决定，可能导致随机崩溃）。

复现命令见 `识别逻辑逐行讲解.md` 第 7 节。

## 怎么编译 / 怎么用

### 视觉端（Ubuntu 虚拟机）

```bash
# 1) 把本文件夹里的 Vision_Code 覆盖回原工程的 Vision_Code（或直接当独立工程用）
#    注意：一定要整份覆盖，Struct.hpp 和 Track.cpp 必须同时更新，否则帧长不一致！

# 2) 必须先用 flatc 重新生成 flatbuffers 头文件（VisionData.fbs 改了）
cd Vision_Code/config/flatbuffers
flatc --cpp --bfs -o ../autogenerated_flatbuffers \
      VisionData.fbs CaptureInformation.fbs CarData.fbs RawImage.fbs \
      Time.fbs FrameTransform.fbs FrameTransforms.fbs Quaternion.fbs \
      Vector3.fbs Vector2.fbs Point2.fbs Point3.fbs Duration.fbs \
      KeyValuePair.fbs PackedElementField.fbs Color.fbs
# （命令以你工程实际的生成脚本为准，核心是 VisionData.fbs 必须重新生成）

# 3) 正常 cmake 构建
cd ../.. && mkdir -p build && cd build
cmake .. && make -j$(nproc)
```

### 电控端（Keil / armclang）

把 `Electric_Control_Code/Application/` 下这 4 个文件覆盖回原工程：

- `DeviceLayer/Sensor/vision_sensor.h`
- `DeviceLayer/Sensor/vision_sensor.c`
- `ProtocolLayer/vision_protocol.c`
- `ModuleLayer/axis.c`（**可选**，含默认关闭的宏开关）

`vision_sensor.h` 里有一行编译期自检：

```c
_Static_assert(sizeof(vision_rx_info_t) == 22, "vision_rx_info_t size mismatch with vision side!");
```

如果编译报这句话，说明结构体被人改过、帧长和视觉端不一致 —— 这时候**不要**去改这个数字，要去查为什么长度变了。

### 离线校验（不用接相机和飞控板）

```bash
cd verify

# ① 帧结构 / 单目测距 / 角度解算（21 项）
g++ -std=c++17 -O2 -Wall -I. verify_frame.cpp CRC_Check.cpp -o verify_frame
./verify_frame

# ② 识别链路坐标换算（18 项，自洽定标法）
g++ -std=c++17 -O2 -Wall verify_detect.cpp -o verify_detect $(pkg-config --cflags --libs opencv4)
./verify_detect

# ③ 用桩头把修正后的识别代码真编译一遍（应 0 error / 0 warning）
g++ -std=c++20 -Wall -Wextra -O1 compile_check_detect.cpp -o compile_check_detect $(pkg-config --cflags --libs opencv4)
./compile_check_detect
```

Windows + MinGW 下把输出名换成 `verify_frame.exe` 即可，命令一样。

预期输出结尾：`校验结束: 全部通过, 失败 0 项`。

## 下发帧最终长什么样（22 字节）

| 偏移 | 长度 | 类型 | 字段 | 含义 |
|---:|---:|---|---|---|
| 0 | 1 | uint8 | `header` / `SOF` | 固定 `0xA5` |
| 1 | 1 | uint8 | `CRC8` | 帧头区校验字节1 |
| 2 | 1 | uint8 | `CRC8_reserved` | 帧头区校验字节2（CRC8 实际落点） |
| 3 | 4 | float | `pitch_error` | **俯仰角误差 (rad)**，正=目标偏上 |
| 7 | 4 | float | `yaw_error` | **偏航角误差 (rad)**，正=目标偏右 |
| 11 | 4 | float | `roll_error` | **横滚角误差 (rad)**，正=画面顺时针倾 |
| 15 | 4 | float | `distance` | **到目标直线距离 (m)**，0=无效 |
| 19 | 1 | uint8 | `target_status` | 0=丢失 1=找到 |
| 20 | 2 | uint16 | `CRC16` | 整帧 CRC16 |

小端序；视觉端与电控端 `sizeof` 都是 22，已实测验证。

## 三个必须注意的点

1. **两边必须同时升级**。帧长从 11 变 22，只烧一边会一直 CRC 失败、飞控收不到任何数据（`vision_sensor` 会因 `offline_max_cnt` 超限判为离线并进入保护，是安全的，但自瞄不工作）。

2. **`target.width_m` 要实测标定**，它直接决定距离的绝对精度。方法：把靶放在已知距离 `Z0`（如 2.00 m），量出检测框宽度 `w0` 像素，则 `width_m = Z0 * w0 / fx`。别用默认的 0.15。

3. **`axis.c` 里的宏默认是 0**：

   ```c
   #define VISION_PITCH_CTRL        0
   #define VISION_DIST_FEEDFORWARD  0
   ```

   也就是说：协议、数据、Y 轴代码都到位了，但**控制行为和改造前一模一样**，不会因为 PID 没调就出问题。等你台架上把 `axis_pitch_pid` 的 `kp/ki/kd` 和方向确认好，再把 `VISION_PITCH_CTRL` 改成 1。

## 常见问题

**Q: 编译报 `'vision_rx_info_t' size mismatch`？**
A: `vision_sensor.h` 的结构体和视觉端帧长对不上。检查是不是漏改了某个字段，或者 Keil 工程里有另一份结构体定义。

**Q: 飞控收到的 `distance` 一直是 0？**
A: 三种可能：① 目标框像素宽高 < 1px；② 算出的距离小于 `distance.min_m`（0.5 m）；③ `target.width_m` 或 `fx` 填错导致距离超量程被钳位。先看视觉端调试窗口的 `dist:` 显示。

**Q: `pitch` 一直是某个固定值不接近 0？**
A: `camera.cy` 填错了。本工程用 640×640 原图，`cy` 应该是 `height/2 = 320`（`sensors.json` 里那个 `208` 是 384 高图的上半幅，不能直接用）。

**Q: `roll` 数值很奇怪？**
A: 当前 `roll` 是用"轴对齐检测框的长宽比"近似估算的，本身就是粗值。飞控侧没用它控制任何轴，仅仅是传上去 + 回放用。要精确 roll 请见总结文档第 11 节。

**Q: 目标丢失后飞控还在追旧角度？**
A: 本版已修：丢失时视觉端会把 4 个量清零并持续下发 `target_status = 0`；电控端 X 轴（以及启用后的 Y 轴）会切到 `TOANGLE` 保护，锁在最后角度而不是继续加速。
